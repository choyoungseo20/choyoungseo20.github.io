이력서를 정리하는 김에, 최근 고민하고 있는 캐시 경계 문제도 함께 정리해 둔다.

우리 시스템의 금융상품 설명 콘텐츠 조회 API는 `(ticker, trade_date)` 로 검토·승인된 콘텐츠를 반환한다. 응답은 고객별로 달라지지 않으므로 캐시 키에 고객 식별자가 들어가지 않는다. 현재는 단일 인스턴스에 Caffeine 인프로세스 캐시를 두고 TTL 3초로 운영한다.

이 구성을 증권사 관리 환경의 로드밸런서 뒤 4대로 확장한다고 가정하면, 가장 먼저 나오는 결론은 보통 이것이다. "인프로세스 캐시는 공유되지 않으니 Redis를 넣어야 한다."

앞 문장의 전제는 맞고 결론은 성립하지 않는다. 캐시가 공유되지 않는다는 사실은 관측이고, 공유 캐시가 필요하다는 것은 판단이다. 그 사이에는 무엇을 문제로 정의했는지가 들어가야 한다.

이 글에서는 아래의 일곱 가지를 다룬다.

- 프로세스별 캐시. 4대면 캐시가 4개라는 사실이 실제로 무엇을 바꾸는가.
- 세 가지 문제의 분리. 느린 것, 안 맞는 것, 안 겹치는 것.
- 공유 캐시의 한계. Redis 를 넣어도 남는 stale과 dual-write.
- single-flight의 범위. 요청 수 → 1이 요청 수 → 인스턴스 수가 되는 지점.
- TTL·jitter·refresh·negative cache. 각 장치가 못 하는 일.
- 불변 축과 변경 축. 게시 스냅샷과 현재 상태를 한 객체에 담지 않는 이유.
- 선택에 필요한 지표. hit ratio 하나로는 결정할 수 없다.

> 이 글은 개념 정리다. 4대 확장, Redis 비교, TTL 동시 만료 실험은 계획 단계이며 수치는 다음 글의 로컬 실험에서 실측한다. 현재 확정된 구현은 단일 인스턴스 Caffeine TTL 3초까지다.

## 인스턴스가 4대면 캐시도 4개다

Caffeine 은 JVM 힙 안의 자료구조다. 프로세스 경계를 넘지 않는다. 인스턴스를 4대로 늘리면 캐시 히트율이 4분의 1로 떨어지는 것이 아니라, 서로 독립적인 캐시가 4개 생긴다.

이 차이가 만드는 결과는 두 가지다.

| 단일 인스턴스에서 성립하던 것 | 4대에서 벌어지는 일 |
| --- | --- |
| 같은 키의 첫 요청 1건만 DB를 읽는다 | 각 인스턴스에서 첫 요청이 한 번씩, 최대 4건이 DB를 읽는다 |
| 캐시에 담긴 값이 곧 이 서비스의 현재 응답이다 | 인스턴스마다 다른 시점의 값을 들고 있을 수 있다 |
| TTL 3초 = 정정 반영 지연의 상한 | 상한은 여전히 3초지만, 그 안에서 응답이 갈린다 |
| 프로세스 재시작 1회 = cold start 1회 | 배포·스케일아웃마다 cold start가 인스턴스 수만큼 발생한다 |

주목할 점은 첫 줄과 둘째 줄의 성격이 다르다는 것이다. 첫 줄은 비용이 4배가 되는 문제고, 둘째 줄은 응답이 서로 달라지는 문제다. 같은 원인에서 나왔지만 허용 기준도, 해법도 같지 않다.

## 느린 것, 안 맞는 것, 안 겹치는 것은 다른 문제다

"캐시가 안 좋다"는 진술은 최소 세 가지로 갈린다.

- 성능. 응답이 느리거나 처리량 상한이 낮다. 지표는 p99와 포화 처리율이다.
- 정합성. 차단된 콘텐츠가 계속 나가거나, 정정 전 문구가 보인다. 지표는 최대 스테일 시간과 차단 후 200 응답 수다.
- 공유. 같은 값을 여러 인스턴스가 각자 로딩한다. 지표는 loader 호출 수와 DB SELECT 수다.

셋은 서로 독립적으로 나쁠 수 있다. 히트율이 100%여도 캐시된 값이 차단된 콘텐츠면 정합성 문제다. 정합성이 완벽해도 각 인스턴스가 매번 따로 로딩하면 공유 문제다. 공유가 완벽해도 그 공유 저장소가 네트워크 왕복이면 성능 문제가 새로 생긴다.

Redis 도입 논의가 흐려지는 지점이 여기다. Redis 는 세 번째 축을 직접 다루고, 첫 번째 축을 바꿀 수도 있으며, 두 번째 축은 거의 바꾸지 못한다. 그런데 논의는 보통 세 축을 "Redis 를 넣느냐 마느냐"라는 하나의 질문으로 압축한다.

## 공유 캐시는 DB와의 정합성을 보장하지 않는다

"Redis 를 두면 인스턴스 간 값이 같아진다"는 명제는 조건부로만 참이다. 캐시 계층이 하나일 때만 성립하고, 그때도 DB와 캐시 사이의 정합성은 별개로 남는다.

먼저 L1이 남아 있으면 공유되지 않는다. Caffeine L1 위에 Redis L2를 얹는 구성에서 인스턴스가 보는 값은 L1의 값이다. L2가 최신으로 갱신돼도 L1 TTL이 남아 있는 동안은 이전 값을 반환한다. 계층을 추가하면 공유되는 것은 L2뿐이고, 관측 가능한 응답은 여전히 L1이 결정한다.

캐시와 DB 갱신은 dual-write라는 점도 남는다. 게시 상태가 바뀔 때 DB를 쓰고 캐시를 갱신(또는 삭제)하는 두 개의 쓰기가 생긴다. 둘은 한 트랜잭션이 아니다. 사이에서 프로세스가 죽거나 순서가 뒤집히면 캐시가 DB보다 오래된 값을 들고 남는다. 공유 캐시는 이 문제를 만드는 쪽이지 푸는 쪽이 아니다.

마지막으로 만료는 동시에 일어난다. 공유 키 하나가 TTL로 사라지는 순간, 그 키를 기다리던 모든 인스턴스의 모든 요청이 동시에 miss가 된다. 공유 캐시는 miss도 공유한다.

정리하면 이렇다.

```text
Redis 도입으로 얻는 것:  인스턴스 간 캐시 적중의 공유
Redis 도입으로 얻지 못하는 것:
    - DB ↔ 캐시 정합성      (dual-write는 그대로)
    - L1이 있는 경우의 공유  (관측 값은 L1이 결정)
    - 만료 순간의 부하 평탄화 (오히려 한 점에 모인다)
    - 장애 격리             (새 공용 의존성이 생긴다)
```

## single-flight의 범위는 프로세스 경계에서 끊긴다

현재 구현은 같은 키에 대한 동시 미스를 원자 로더로 합친다. `cache.get(key, loader)` 형태에서 동시에 도착한 N개 요청은 loader 를 1회만 호출하고 나머지는 그 결과에 합류한다. 이것이 single-flight다.

인스턴스가 늘어나면 이 보장의 범위가 달라진다.

| 구성 | 동시 미스 N건에 대한 loader 호출 |
| --- | --- |
| 1대, single-flight 없음 | N |
| 1대, 원자 로더 | 1 |
| 4대, 원자 로더 | 최대 4 (인스턴스당 1) |
| 4대 + 공유 L2, 분산 락 없음 | 최대 4 (L2 miss가 동시에 나면) |

핵심은 원자 로더가 요청 수 의존성을 인스턴스 수 의존성으로 바꾼다는 것이다. N에 비례하던 것이 인스턴스 수라는 상수에 비례하게 된다. 초당 10,000건이 하나의 인기 종목에 몰려도 loader 호출은 TTL 주기마다 4건이다.

### "스탬피드"라는 말을 언제 쓸 수 있는가

여기서 용어를 좁혀 둘 필요가 있다. 캐시 스탬피드는 TTL 만료 순간 loader/DB 호출이 동시 요청 수에 비례해 폭증하는 현상이다. 인스턴스 수만큼 호출이 늘어나는 것은 스탬피드가 아니라 상수배다.

이 구분이 실무에서 중요한 이유는, 분산 락이나 확률적 조기 갱신 같은 장치의 정당성이 전적으로 여기에 달려 있기 때문이다. 실제 부하가 요청 수에 비례한다면 그 장치들이 필요하고, 인스턴스 수 수준에 머문다면 복잡도만 늘리는 셈이다. 우리 시스템에서 이 수치는 아직 측정하지 않았다. 4대 환경에서 TTL 동시 만료 시 loader 호출 수를 세는 것이 다음 실험의 판정 항목 중 하나다.

## TTL·jitter·refresh·negative cache는 각각 다른 문제를 푼다

캐시 주변 장치들은 이름이 익숙해서 한 묶음처럼 보이지만, 해결 대상이 겹치지 않는다.

| 장치 | 해결하는 문제 | 해결하지 못하는 문제 |
| --- | --- | --- |
| TTL | 무효화 경로 없이도 stale의 상한을 보장 | 상한 안에서의 불일치, 만료 순간의 동시 miss |
| TTL jitter | 여러 키가 같은 순간 만료되며 생기는 피크 | 단일 hot key의 만료 (키가 하나면 흩뿌릴 대상이 없다) |
| 비동기 refresh | 만료 시점에 요청이 로딩을 기다리는 지연 | 아무도 조회하지 않던 키의 첫 요청(cold start) |
| negative cache | 결과 없음(204)이 매번 DB를 치는 문제 | 그 사이 생성된 데이터의 즉시 반영 |
| 분산 락 | 인스턴스 간 중복 로딩 | 락 획득 실패 시의 대기·타임아웃 설계 부담 |

특히 jitter 는 오해가 잦다. jitter 는 만료 시점이 동일한 키가 여럿일 때 그 시점을 흩뿌린다. 요청의 90%가 하나의 hot key 에 몰리는 시나리오에서는 흩뿌릴 키가 사실상 하나이므로, 그 키의 만료 순간에 몰리는 동시 요청은 jitter 로 줄지 않는다. 그 부하를 줄이는 것은 jitter 가 아니라 single-flight 다.

우리 시스템의 TTL 3초도 성능 파라미터가 아니다. 프로세스 간 무효화 경로가 없는 상태에서 차단·정정이 반영되기까지의 최대 지연을 3초로 묶는 값이다. 값의 근거가 성능이 아니라 정합성에 있으므로, 캐시 전략을 바꿔도 이 상한은 별도로 지켜야 한다.

## 불변 콘텐츠와 변경 가능한 현재 상태는 같은 객체가 아니다

현재 캐시 키 `(ticker, trade_date)` 가 가리키는 것은 "이 종목의 이 날짜 현재 응답"이다. 이 값은 두 종류의 데이터가 섞여 있다.

- 불변 축. 게시된 콘텐츠 본문이다. 게시 식별자나 `콘텐츠 ID + 버전` 으로 지정하면 그 내용은 다시 바뀌지 않는다.
- 변경 축. 현재 발행 버전이 무엇인지, 차단됐는지, 제공 범위에 포함되는지, 최신 면책 문구가 무엇인지다.

둘을 한 객체로 캐싱하면 캐시 정책이 항상 변경 축에 끌려간다. 본문은 영원히 재사용해도 되는데, 차단 여부 때문에 TTL 3초를 걸어야 한다. 캐시의 이득 대부분이 불변 축에서 나오는데 비용은 변경 축이 결정하는 구조다.

축을 나누면 각각에 맞는 정책을 줄 수 있다. 불변 축은 버전 키로 길게 캐싱하고(같은 키가 다른 값을 가질 수 없으므로 무효화 자체가 필요 없다), 변경 축은 짧은 TTL이나 조회 시 확인으로 다룬다. 대신 조회 한 번에 확인이 두 번 들어가므로, 나누는 것이 항상 이득은 아니다.

여기서 확인되는 것은 캐시 TTL 결정이 성능 튜닝이 아니라 데이터 모델 결정이라는 점이다. "몇 초로 할까"에 답하려면 먼저 "이 키가 가리키는 값이 바뀔 수 있는가"에 답해야 한다.

## 메모리 용량과 처리량은 같은 축이 아니다

로컬 실험에서 Redis 에 `maxmemory 1GB` 를 걸 예정이다. 이 숫자는 저장 용량 조건 하나를 정할 뿐, 다음 어느 것도 뜻하지 않는다.

- 초당 처리 가능한 명령 수
- 동시 연결 수 상한과 클라이언트 대기
- 명령 지연과 그 꼬리 분포
- 네트워크 입출력 대역

"요청이 10만 건이니 1GB가 찬다"는 추론은 성립하지 않는다. 저장되는 것은 요청이 아니라 키이고, 사용량은 `키 수 × 값 크기` 로 결정된다. hot key 시나리오에서 키 수는 종목 수 수준이므로 메모리는 거의 남고, 병목이 생긴다면 연결이나 명령 지연 쪽이다.

이 둘을 구분해야 판정 기준을 미리 쓸 수 있다. 지연이 올라갔는데 `used_memory` 에 여유가 있고 eviction 이 0이라면 메모리 가설은 기각된다. 실험 전에 기각 조건을 적어 두는 이유는, 결과를 보고 나서 가설을 고치지 않기 위해서다.

## hit ratio 만으로는 캐시 전략을 고를 수 없다

캐시를 붙이고 나면 히트율부터 본다. 그런데 히트율은 캐시가 동작했는지를 말할 뿐, 그 동작이 무엇을 바꿨는지는 말하지 않는다. 앞선 실험에서 히트율 99.9%를 달성하고도 p99가 거의 그대로였던 경험이 그 사례다. 병목이 읽기가 아니었기 때문이다.

선택에 필요한 지표는 최소한 다음과 같다.

| 결정할 것 | 필요한 지표 |
| --- | --- |
| 인스턴스별 캐시로 충분한가 | loader 호출 수와 DB SELECT 수 (요청 수 대비 비율이 아니라 절대 건수) |
| 공유 캐시가 DB를 지키는가 | 신규 인스턴스 투입·전체 재기동 시 DB 호출 피크 |
| 공유 캐시가 새 병목인가 | Redis 명령 지연·연결 풀 대기와 API p99 의 동반 상승 여부 |
| 정합성이 허용 범위인가 | 게시 변경·차단 후 모든 인스턴스 반영까지 걸린 시간, 차단 후 200 응답 수 |
| 장애를 감당할 수 있는가 | 공유 캐시 정지 시 오류율과 DB로 열리는 동시 로딩 수 |

이 목록의 성격에 주목할 만하다. 절반은 성능 지표가 아니라 정확성과 장애 지표다. 캐시 선택이 성능 문제로만 보이는 동안에는 이 절반이 측정 대상에 들어오지 않고, 그러면 어떤 수치를 얻어도 결정을 내릴 수 없다.
