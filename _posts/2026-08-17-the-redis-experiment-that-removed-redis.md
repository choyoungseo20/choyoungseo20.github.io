[앞 글](/posts/multi-instance-does-not-require-redis/)에서 인프로세스 캐시가 공유되지 않는다는 사실만으로 공유 캐시가 정당화되지는 않는다고 정리하고, 무엇을 재야 하는지까지만 적은 뒤 `[실측 예정]`으로 닫았다. 이 글이 그 측정이다.

실험은 Redis 를 넣으려고 시작했고, 끝났을 때 Redis 를 빼기로 결정했다.

결론을 먼저 적는 이유는 이 글의 내용 대부분이 처음 세운 가설이 기각되는 과정이기 때문이다. 특히 "공유 캐시가 콜드 스타트에서 DB를 보호한다"는 예상은 정확히 반대 방향으로 나왔다.

이 글에서는 아래의 일곱 가지를 다룬다.

- 목표 부하 포기. 10,000 rps 를 만들지 못한 장비에서 무엇을 유효 측정값으로 삼았는가.
- 본 비교. 네 전략의 응답 지연이 서로 구별되지 않았다.
- 콜드 스타트. 공유 캐시 단독 구성이 DB를 가장 세게 때렸다.
- 동시 만료. 스탬피드는 없었고 jitter 는 완화할 피크를 찾지 못했다.
- 장애와 정합성. fail-open 지연 상한이 타임아웃 값으로 유계였다.
- 쓰기 경로. 감사 기록을 되살리면 전략 차이가 사라진다.
- 결정과 재검토 트리거. 무엇을 기각했고 무엇이 바뀌면 다시 재는가.

> 측정 환경은 로컬 Docker Compose(Apple M5 Pro)이며 부하 발생기와 서버가 같은 머신에서 돌았다. 따라서 아래 수치는 운영 환경의 절대 용량이 아니라 전략 간 비교 기준이다. 구성은 nginx 라운드로빈 + 조회 API 4대(각 1 CPU/768MB) + 전용 PostgreSQL(2 CPU) + Redis 7(maxmemory 1GB, persistence off), Prometheus 5초 스크레이프. L1 Caffeine TTL 2초, L2 Redis TTL 3초다.

## 목표 부하를 먼저 포기하고 임계점을 찾았다

목표로 둔 시나리오는 인기 종목 급등 시 10초간 10만 요청, 즉 10,000 rps 였다. 이 장비는 그 부하를 만들지 못했다.

단계별로 요청률을 올려 임계점을 먼저 찾았다. 1대 구성은 1,600~2,000 rps, 4대 구성은 2,800~3,200 rps 에서 임계점이 왔고 포화 실효 처리율은 약 5,700 rps 였다. 부하 발생기가 서버와 자원을 나눠 쓰는 환경이므로 이 위쪽은 무엇을 측정하든 발생기 병목과 섞인다.

그래서 표기 규율을 정했다. "10만 사용자를 처리했다"고 쓰지 않고 "로컬 Compose 환경에서 최대 약 5.7k rps 까지 검증했다"고 쓴다. 이 규율 아래 이 글의 측정은 부하 run 75회로 이뤄졌다. 접근 분포의 경계를 재는 후속 29회는 [다음 글](/posts/measuring-the-cache-boundary/)에서 다룬다. 전략 비교는 1대 구성까지 무결하게 따라오는 공통 요청률 1,600 rps 에서 수행했다. 한 구성이 이미 포화된 지점에서 비교하면 캐시 전략의 차이가 아니라 포화 순서를 재게 된다.

읽기 경로 비교를 위해 감사 기록과 요청 메트릭의 동기 쓰기를 부하 프로필에서만 껐다. 캐시 효과와 쓰기 병목이 섞이는 것을 막기 위한 분리이며, 기본 프로필의 쓰기 계약은 유지했다.

## 네 전략의 응답 지연은 서로 구별되지 않았다

1,600 rps, 3분, 3회 반복 중앙값이다.

| 모드 | API 수 | p99 | DB loader 호출(3분) |
| --- | ---: | ---: | ---: |
| 캐시 없음 | 1 | 1.4ms | 287,998 |
| 인프로세스만 | 1 | 1.1ms | 268 |
| 캐시 없음 | 4 | 1.9ms | 287,997 |
| 인프로세스만 | 4 | 1.5ms | 1,062 |
| 공유 캐시만 | 4 | 1.9ms | 192 |
| 2계층 | 4 | 1.4ms | 146 |

L1 적중률은 99.6~99.9%였고 전 모드에서 오류는 0이었다.

먼저 눈에 들어오는 것은 p99 열이다. 캐시가 아예 없는 구성까지 포함해 전부 1~2ms 안에 들어온다. 이 요청률에서는 DB 조회 자체가 충분히 싸서, 캐시가 있든 없든 응답 지연에 나타나지 않는다. 이 실험에서 캐시의 효과는 전부 DB loader 축에서만 관측된다.

![](/assets/img/posts/2026-08-17-the-redis-experiment-that-removed-redis-01.png)

앞 글에서 히트율만으로는 결정할 수 없다고 적은 이유가 이 표에 그대로 있다. 적중률 99.9%와 p99 1.5ms 를 나란히 두면 캐시가 응답을 빠르게 만든 것처럼 읽히지만, 대조군인 캐시 없음도 1.9ms 다.

loader 축을 보면 차이는 분명하다. 288,000건의 요청이 4대 인프로세스 구성에서 1,062회의 DB 로딩으로 접혔다. 이 값은 이론치(키 3종 × TTL 주기 90 × 4대)의 0.98배다. 요청 수에 비례하던 것이 인스턴스 수에 비례하는 상수로 바뀌었다는 뜻이며, 앞 글에서 정의한 대로 이것은 스탬피드가 아니다.

![](/assets/img/posts/2026-08-17-the-redis-experiment-that-removed-redis-02.png)

그렇다면 공유 캐시가 1,062을 192로 더 줄여주는 몫은 얼마나 가치 있는가. 초당 5.9회를 초당 1.1회로 줄인다. 같은 시간 PostgreSQL 은 초당 약 4,800 트랜잭션을 처리하고 있었고 커넥션 풀 대기는 0이었다. 여유가 3배 남은 자원에서 초당 4.8회를 아끼는 셈이다.

## 콜드 스타트에서 공유 캐시가 DB를 가장 세게 때렸다

여기가 가설이 뒤집힌 지점이다. 예상은 "공유 캐시가 콜드 스타트의 DB 피크를 흡수한다"였다.

모든 캐시를 비우고 재기동한 직후 30초간의 DB loader 호출이다.

| 모드 | 30초간 loader 호출 | 초당 피크 |
| --- | ---: | ---: |
| 인프로세스만 | 92 | 5.7 |
| 공유 캐시만 | 1,658 | 85 |
| 2계층 | 17 | 1.0 |

공유 캐시 단독 구성이 인프로세스만 쓰는 구성보다 18배 많은 DB 로딩을 냈다. 이 실험에서 관측한 유일한 진짜 스탬피드이며, 요청 수에 비례하는 폭증이라는 정의를 만족한다.

원인은 첫 로딩의 소요 시간이다. 캐시가 완전히 빈 상태의 DB 조회는 수백 ms 가 걸린다. 그 사이에도 1,600 rps 는 계속 도착하고, 공유 캐시 경로에는 도착한 요청을 하나의 로딩으로 합칠 장치가 없어 전부 DB로 흘러간다. 2계층 구성에서 이 폭발이 17건으로 접힌 이유는 L2 가 있었기 때문이 아니라 L1 의 원자 로더가 동시 미스를 1회로 합류시켰기 때문이다.

### 잃어버린 것은 Redis 의 결함이 아니다

정직하게 적어야 할 부분이 있다. 이 결과는 Redis 가 스탬피드에 취약하다는 뜻이 아니다. 공유 캐시 경로에 요청 코얼레싱을 구현하지 않은 우리 구현 선택의 성질이다. 분산 락이나 인스턴스 로컬 코얼레싱을 얹으면 완화된다.

그래서 교훈은 Redis 에 대한 것이 아니라 이동에 대한 것이다. 인프로세스 캐시에서 공유 캐시로 옮기면, 로컬 캐시가 공짜로 주고 있던 single-flight 를 잃는다. 이 보장은 `cache.get(key, loader)` 한 줄에 딸려 오던 것이어서 설계 문서에 항목으로 적힌 적이 없고, 그래서 이동 시 체크리스트에서 빠진다. 앞 글에서 single-flight 의 범위를 따로 한 절로 다룬 이유가 이것이었다.

## TTL 동시 만료는 스탬피드가 아니었고, jitter 는 완화할 피크를 찾지 못했다

전 인스턴스의 캐시를 동시에 만료시키고 1,600 rps 버스트(9.6만 요청)를 넣었다.

만료 온셋 10초 구간의 DB loader 호출은 1.5~1.8건이었다. L1 miss 는 8~9건으로 이론치(키 1종 × 4대 × TTL 주기)와 일치했고, 그 miss 를 L2 가 받아 접었다. 요청 수 비례 폭증은 없다. 동시 만료 스탬피드 가설은 기각이다.

jitter 도 함께 봤다. jitter 0과 2초를 비교했을 때 전 지표가 반복 편차 안에 들어왔다. 효과가 없었다기보다 완화할 피크가 애초에 없었다. 60초 동안 L2 재적재가 20건뿐인 상황에서는 흩뿌릴 대상이 없다. 앞 글에서 jitter 는 동시에 만료되는 키가 여럿일 때 쓰는 장치이고 단일 hot key 에는 무력하다고 적었는데, 이 시나리오는 정확히 그 조건이었다.

사정거리를 한정해 둔다. 이 실험의 hot key 는 사실상 한 종목이다. 워킹셋이 수백 종목이고 그 키들이 같은 순간에 적재됐다면 결과가 다를 수 있으며, 그 국면은 재지 않았다.

## Redis 장애 실험이 Redis 없이도 안전하다는 것을 증명했다

2계층 구성에서 부하 중 Redis 를 60초간 정지시켰다.

오류는 0이었고 1,600 rps 는 평탄하게 유지됐다. DB loader 는 초당 5.15회로, L1 단독 이론치인 초당 6회 수준이다. 요청률 초당 1,600 대비 310분의 1이다. L2 가 사라져도 L1 이 요청 수 비례 폭증을 막았다.

지연은 올라갔다. p99 가 1.0ms 에서 313~319ms 가 됐는데, 이 값은 명령 타임아웃 150ms 의 정확히 2배다. 요청 하나가 L2 get 실패와 put 실패를 직렬로 겪기 때문이며, 다시 말해 fail-open 의 지연 대가가 타임아웃 값으로 유계였다. 시간이 지나며 악화되는 연쇄는 없었다.

복귀 시 재적재 herd 도 없었다. Redis 가 돌아온 뒤 L2 miss 는 초당 0.76회 이하로, 평시 0.85회보다 오히려 낮았다.

역설적인 결과다. 장애 실험이 확인해 준 것은 Redis 가 있을 때의 견고함이 아니라, DB를 지키고 있는 주체가 L1 이라는 사실이었다.

## 차단은 캐시 표면 밖에 있고, 새 게시는 가산 TTL 상한 안에 있었다

부하 중에 새 게시와 차단을 주입해 반영 시간을 측정했다.

| 변경 유형 | 전 인스턴스 반영까지 | 기준 |
| --- | ---: | --- |
| 새 게시 | 4.22~4.45s | 스테일 SLO 5s |
| 차단(제공 범위 OFF) | 0.00~0.01s | 즉시 |

새 게시는 SLO 안에 들어왔다. 5초라는 SLO 자체가 L1 2초와 L2 3초의 가산 상한에서 나온 값이므로, 이 측정은 새로운 보장을 만든 것이 아니라 가산 논증과 모순이 없음을 확인한 것이다. 3회 반복이 모두 비슷한 TTL 위상에서 실행돼 최악 위상은 측정되지 않았다. 5초 보장의 근거는 여전히 측정이 아니라 TTL 가산 논증이다.

차단이 사실상 즉시인 이유는 캐시와 무관하다. 차단 판정이 캐시 앞단에 있어 요청마다 DB를 확인하므로, 차단 상태는 캐시 표면 밖에 있다. 앞 글에서 불변 축과 변경 축을 나눠야 한다고 적은 것이 이미 부분적으로 적용돼 있었던 셈이다. 본문은 캐시하고, 가장 위험한 변경 축은 캐시하지 않는다.

## 감사 기록을 되살리면 캐시 전략의 차이가 사라진다

읽기 경로에서 껐던 동기 쓰기를 되살렸다. 200 응답마다 감사 기록과 요청 메트릭 INSERT 가 각각 한 건씩 들어간다.

쓰기 대가는 초당 3,200 트랜잭션 증가였고, 200당 INSERT 2건이라는 이론과 0.4% 오차로 일치한다. 중요한 것은 이 증가폭이 인프로세스 구성과 2계층 구성에서 완전히 동일했다는 점이다. 캐시 전략을 무엇으로 바꿔도 쓰기 병목은 그대로 남는다.

이전 실험에서 적중률 99.9%를 달성하고도 p99 가 거의 그대로였던 이유와 같은 구조다. 전체 경로에서 요청당 DB 작업이 다섯 건이라면 캐시가 지우는 것은 그중 읽기 한 건이다.

지연 꼬리는 두 구성에서 갈렸다.

| 모드 | 읽기 경로 p99 | 전체 경로 p99 |
| --- | ---: | ---: |
| 인프로세스만 | 1.5ms | 4.2ms |
| 2계층 | 1.4ms | 5.7~11.5ms |

2계층 구성에서만 꼬리가 더 나빠졌고 커넥션 풀 대기가 간헐적으로 관측됐다(pending 최대 337). 쓰기가 커넥션을 점유하는 동안 L2 왕복이 요청 처리 시간을 늘려 겹치는 것으로 보이지만, 깨끗한 반복이 2회뿐이어서 방향만 신뢰하고 크기는 미확정으로 남긴다.

## 인프로세스 캐시를 유지하고 Redis 를 기각했다

두 후보를 각각의 이유로 기각했다.

공유 캐시 단독은 콜드 스타트에서 유일한 진짜 스탬피드를 만들었다. 코얼레싱을 추가하면 막을 수 있지만, 그것은 인프로세스 캐시가 이미 갖고 있는 것을 다시 구현하는 일이다.

2계층은 이득이 실재했다. 측정 중 4대째 인스턴스를 합류시키자, 신규 인스턴스의 L1 miss 초당 1.5회가 전부 L2 적중으로 흡수되며 클러스터 전체 DB loader 가 평평했다(30초당 22 → 22). 인프로세스만이었다면 초당 0.8회에서 2.3회로 약 3배가 됐을 값이다. 역할 분담이 여기서 선명해진다. 폭발 방어는 L1 의 코얼레싱이 맡고, 증설분의 상시 상환은 L2 가 맡는다.

문제는 그 이득의 절대값이 초당 1.5회라는 것이다. 대가는 전체 경로 지연 꼬리 악화, TTL 두 계층의 운영 복잡도, 새로운 공용 장애 의존성, 그리고 증권사 관리 환경에 컴포넌트를 하나 더 반입하는 절차 비용이다. 초당 1.5회로 이 목록을 지불할 근거는 만들어지지 않았다.

기각이 아니라 보류이므로 재검토 조건을 함께 적었다.

| 재검토 트리거 | 현재 값 |
| --- | --- |
| 워킹셋이 수백 종목으로 확대 | 키 3종 |
| 로더가 고비용화(무거운 조립·외부 호출) | 약 1ms |
| 인스턴스가 수십 대 규모 | 4대 |
| DB가 다른 워크로드와 공유되는 자원이 됨 | 전용, 여유 3배 |
| 캐시 외 용도로 Redis 가 이미 도입됨 | 없음 |

하나로 압축하면 판별식은 이렇다. 같은 값을 (여러 프로세스가) × (비싸게) × (많이) 다시 만들고 있는가. 둘 이상이 참이면 공유 캐시가 유리해지고, 전부 거짓이면 로컬 캐시가 단순하다. 우리 경우는 첫째만 참이었다.

## 회고

로컬 측정의 한계는 그대로 남는다. 부하 발생기와 서버가 같은 머신이었고, 목표 10,000 rps 에는 도달하지 못했으며, 워킹셋은 사실상 단일 키였고, 전체 경로 꼬리 비교는 반복이 부족했다. 운영 배치 전에는 별도 부하 발생 노드에서 워킹셋을 실제 종목 수로 늘려 다시 재야 한다.

그럼에도 이 실험이 결정에 충분했던 이유는 측정값이 좋았기 때문이 아니라, 결정을 뒤집을 조건을 숫자로 적을 수 있게 됐기 때문이다. 앞 글에서 "지표 없이는 결정할 수 없다"고 적었는데, 지표가 생긴 뒤 결정은 도입이 아니라 보류였다.
